# Craft 三模式与可插拔内核实施计划

状态：已实施并在 2026-11-05 收敛产品命名与领航编排。
日期：2026-11-03。  
适用范围：`craft` 与 `craft-workbench`。  

一句话结论：Craft 保持一套 Runtime，用“灵策（`workshop`） / 观象（`control`） / 领航（`pilot`）”三种入口投影分别服务项目协作、任务治理和统一并发托管；内核只保留最小控制面，可选能力与插件页面按需加载。

## 摘要

- 三种模式是同一 Craft Runtime 的展示投影，共享 Task、Run、Approval、Evidence 和会话状态，不建立三套 Agent 或三套 Store。
- 领航采用任务级并发：领航者识别并拆分任务，每个任务只路由给一个执行 Agent；不同任务可以并发。执行 Agent 内部可以调用多个只读专家。
- 领航编排采用“规则硬门、模型建议”：Mainer 与 Router 的整理、去重、选择和排队不消耗模型；Worker 只复用 Codex / Claude / DSH / Craft 的既有执行链路。
- 监督者可以暂停或阻断，监督模型只给风险与验收建议，不拥有批准、修改或放行权。
- 当前“文件夹分组不生效”的根因是：原生会话创建 Task 时只保存 `workspace`，没有写入 `project_id`；UI 却按 `project_id` 分组。修复为以规范化目录作为工作区身份，同时保留可选的项目语义。
- 内核只拆分可选产品能力，不把所有核心模块插件化。默认启动只加载内核、插件元数据和路由所需描述；能力模块、插件运行时和插件页面按需加载。

## 现状判断

- 当前 Workbench 主界面主要由单体 `workbench/app.js` 驱动，已有 `project-shell.js`、`entry-*` 等历史入口没有接入主启动链路。
- 现有 Task 分组逻辑读取 `task.project_id`，但原生会话创建任务时只提交标题、目标、模型和权限，没有提交工作区或项目标识，因此任务落入“默认”分组。
- 现有插件 manifest 已支持 Skill、MCP、Hook 和界面元数据，但尚未定义插件页面贡献协议。
- 现有内核已具备并发 DAG、只读 Sub-agent、Expert Profile、审批、队列和恢复原语；缺少的是领航产品层的意图拆分、路由、监督和统一交互。

## 产品与交互

### 全局模式

- 标题栏提供“领航 / 观象 / 灵策”高可见度全局切换，并始终标明当前模式。
- 首次进入领航；之后恢复上次使用的模式。切换模式会落到该模式自己的首页，而不是把同一页面换一层导航。
- 切换模式不中断正在运行的任务，也不改变任务权限或执行事实。
- 模式切换会重新加载单文档应用，清空 WebView 中残留的计时器和挂载；执行事实保存在服务端 Task/Run 中，不依赖页面内存。
- 当前领航会话 ID 保存在本地偏好中，重载或切回模式后仍可恢复同一条任务流；存储值只允许安全标识符。
- 三种模式读取同一份服务端状态；任何模式中的操作都通过现有 Task、Approval、Evidence 和 Session API 完成。

### 灵策（`workshop`）

- 左侧导航只保留“新建会话、能力、工作区、设置”。
- “能力”是可折叠分组，只包含“插件、模型”；不再出现“其他”。
- “工作区”按规范化本地目录分组，工作区下展示会话与任务。
- 无法从历史会话推断目录的任务进入“未绑定目录”，不猜测、不删除。
- “新建会话”先选择工作区，再选择 Codex、Claude、DSH 或 Craft 内部模型、模型和权限。
- 默认使用上次工作区和执行器；不自动切换供应商，也不静默选择付费模型。
- 技能、连接器、Memory、Knowledge、Experience、Codebase 和评测页面不再作为一级导航，改为插件贡献页。

### 观象（`control`）

- 一级入口收敛为“我的任务、待我批准、执行配置、权限、设置”。
- 首页是“我的任务”，页头只有一个“新建任务”入口；进度、审批与异常在同一工作面持续可见。
- “待我批准”汇总当前工作区的人工审批、阻塞问题和需要人工裁决的监督结果。
- “我的任务”展示排队、运行、待批准、待输入、完成、失败和未知状态；任务卡提供“新建会话”按钮。
- “新建会话”在控制台打开新建抽屉，创建成功后停留在控制台并插入“我的任务”；需要细调时再跳转工坊。
- “权限”展示全局默认、工作区覆盖、执行模板或任务覆盖及最终生效结果；只允许逐级收紧，不能突破只读安全底线。
- 权限页同时展示可撤销的 `ApprovalGrant`，包括动作指纹、影响范围、风险等级和到期时间。

### 领航（`pilot`）

- 中央只保留连续对话区、必要交互卡和底部输入框；模型、路由、改派和权限配置收在局部控件中，不形成第二套配置后台。
- 输入框附近只保留并发上限、执行状态和必要的 `+` 控件；设置从侧栏底部进入，不设置常驻主导航。
- 一次输入可以自动拆成多个独立任务并排队。
- 只有目标、权限、风险或工作区不明确时才在输入框上方显示阻塞式追问；不影响安全行动的非关键歧义可以作为显式假设继续。
- 任务卡显示工作区、执行模板、模型、权限、路由理由、排队或运行状态、监督结论。
- 任务开始前允许在任务卡中改派执行模板；改派保留原路由理由与操作记录。
- 审批卡显示动作、目标、影响范围、风险等级、指纹和有效期，提供“仅批准一次、批准并记住、拒绝”。
- 高风险动作不显示“记住”；所有已记住的授权都可以在控制台权限页撤销。
- 领航定时对账 Codex / Claude / DSH 原生会话链接，只读取 `WorkbenchAgentSessionLink` 的终态，不重发结果未知的回合。
- 服务端每 2 秒对账所有仍有运行或排队路由的打开会话，页面关闭也不影响终态收口、并发槽释放与最终复查。
- 终态成功释放并发槽并继续排队；终态失败或状态未知会释放当前槽、标记待人工核对，并进入 Reviewer 的硬门结果。
- 任务完成后在对话中生成结果卡，展示摘要、产物引用、验收结论、监督建议和未解决风险。

### 能力与插件信息架构

- “能力”分组只包含“插件”和“模型”。
- 插件是安装单元；技能、连接器、上下文页面和评测页面都是插件贡献。
- 模型由核心管理，不作为插件；但为了信息架构一致，模型入口放在“能力”分组下。
- 插件详情页统一提供“概览、技能、连接器、页面、设置”等区域。
- 没有自定义页面的插件由宿主根据 manifest 自动生成详情页。
- 首版不允许插件贡献一级导航；插件页面统一挂在插件详情下，保持导航稳定。

建议的插件页面归属：

| 插件 | 贡献页面 |
| --- | --- |
| `craft-context` | Memory、Knowledge、Experience、Codebase |
| `craft-capability` | 能力发现、去重、健康检查与激活建议 |
| `craft-quality` | 评测、Signoff、Canary 与质量证据 |
| `craft` | 核心路由、Task、审批、Evidence 与运行状态 |

## 架构与公共接口

### 领域对象

| 对象 | 职责 | 关键边界 |
| --- | --- | --- |
| `Workspace` | 规范化本地目录及其任务边界 | 不等于整个磁盘，也不等同于 Project Brain |
| `Task.workspace_id` | 把任务绑定到明确工作区 | 保留可选 `project_id`，不把路径当作逻辑项目 |
| `ExecutorTemplate` | 绑定 Provider、模型、权限、能力、Procedure 和预算的执行模板 | 一个任务只能选择一个执行模板 |
| `ExpertTemplate` | 可复用的只读分析与建议模板 | 不拥有写入权，结果不能直接成为事实 |
| `SupervisorProfile` | 风险规则、验收 rubric 和监督模型 | 模型只给建议，规则硬门才可阻断 |
| `PilotSession` | 领航对话、原始输入、拆分任务和并发上限 | 不替代普通 Task |
| `PilotRoute` | 任务到执行模板的路由记录 | 包含理由、置信度、改派历史 |
| `ApprovalGrant` | 可复用的精确审批授权 | 绑定工作区、动作指纹、Policy 和有效期 |
| `PluginWorkbenchContribution` | 插件页面与界面贡献声明 | 不携带任意脚本或主页面权限 |

### 工作区修复与迁移

- 新增 `workspace` 记录，至少包含 `workspace_id`、规范化绝对路径、显示名和可选 `project_id`。
- Windows 路径按大小写不敏感规范化；其他平台使用真实路径规范化。
- Task 新增 `workspace_id`，保留 `project_id`。
- 原生会话创建任务时同时写入 `workspace_id`。
- 历史任务从 `workbench_agent_session_link.workspace` 非破坏回填工作区。
- 无法推断目录的任务保留在“未绑定目录”，不强制归入默认工作区。
- 迁移先执行 dry-run 并输出报告；不删除旧记录，不覆盖用户已有改动。

### 插件页面协议

插件 manifest 增加可选 `workbench` 字段：

```json
{
  "workbench": {
    "schemaVersion": 1,
    "pages": [
      {
        "id": "context",
        "title": "上下文",
        "icon": "layers",
        "kind": "declarative",
        "schema": "./workbench/context.page.json",
        "requires": ["memory", "knowledge", "experience"]
      }
    ]
  }
}
```

声明式页面只允许固定组件：`tabs`、`section`、`rows`、`form`、`actions`、`status`、`artifactList`、`emptyState`、`notice`。所有动作必须绑定白名单 API，不允许任意 HTML、CSS 或 JavaScript。

第二里程碑支持 `kind: "sandboxed"` 页面。沙箱页面使用无 Token 的 opaque-origin iframe、`sandbox="allow-scripts"` 和受限 `postMessage` 协议；宿主校验插件身份、会话和 API 白名单，插件不能读取 Workbench Token 或主页面 DOM。

插件页面按需加载：启动时只读取 manifest 元数据，打开页面时才请求页面 schema 或沙箱资源。插件安装到用户级，按工作区启用或停用；未启用插件不贡献页面。

### 内核懒加载

- 默认内核只注册 Store、路由、策略、审批、证据、Task/Run、Host Adapter 和插件注册表。
- Knowledge、Memory、Experience、Codebase、Eval、Datasec 改为描述符加 `ensureLoaded()` 的动态模块。
- 默认 `craft-mcp` 不加载可选能力；只有对应产品面或插件页面打开时才加载。
- 只拆分可选产品能力，不为“最小化”重写稳定核心内核；是否继续拆分以启动追踪、模块依赖和真实性能数据为依据。
- Workbench 入口只加载模式壳和共享状态；工坊、控制台、领航和插件页各自使用动态 `import()`。
- Tauri 仍只负责窗口、文件选择、原生桥接和 sidecar 生命周期，不承载业务逻辑。

## 领航执行流程

1. 用户输入进入 `PilotIntake`，先由纯程序的 `Mainer` 校验大小、敏感信息、去重、合并并形成 1-8 个普通任务。
2. 只有输入确有歧义时，领航模型才参与识别；模型返回结构化 JSON，只能包含任务、工作区、建议执行模板、依赖关系和阻塞问题。
3. 服务端对模型输出做 schema 校验；模型输出不能直接成为执行授权。
4. 存在阻塞问题时，先返回输入框上方的追问卡，不创建任务。
5. 没有阻塞问题时，创建普通 Task，并写入 `PilotSession`、`PilotRoute` 和 `origin=pilot`。
6. 纯程序的 `Router` 优先按用户显式选择、默认执行器和本机可用执行器确定唯一 Worker；模型输出不能成为执行授权。
7. 任务进入服务端持久队列，默认并发 3、最大 8；超出并发上限的任务显示为排队，不丢失、不重复发送。
8. `Worker` 复用现有原生 CLI 会话或 Craft 内部模型；每个任务只启动一个执行 Agent，写入仍由该执行 Agent 串行完成。
9. 执行 Agent 可在步骤中调用只读专家。专家必须返回假设、反例、Evidence、置信边界和下一步建议；专家结果不能直接成为事实或执行授权。
10. 每个步骤结束后记录执行 Receipt、Trace 和风险信号；确定性规则在步骤边界和最终验收前执行硬门。
11. `Reviewer` 先执行确定性硬门（任务完整性、路由覆盖、工作区绑定、人工待办）；监督模型只在硬门之后提供风险与验收建议，硬门失败时暂停并要求人工处理。
12. 人类批准低风险动作后可创建 `ApprovalGrant`；默认 R0/R1 可按策略自动处理，R2 仅记住精确指纹 24 小时，R3 永不记住。
13. 任务完成后在领航对话中生成结果卡；未知结果不自动重试，也不把连接断开当作任务完成。
14. 经过验证的成功执行可以生成执行模板或专家模板候选，但必须经过现有 Evaluation、Signoff、Canary 流程，不自动发布。

### 审批授权记忆

- `ApprovalGrant` 至少绑定 `workspace_id`、动作类型、规范化参数指纹、`effect`、风险等级、Policy 版本、执行模板版本、有效期和撤销状态。
- 指纹必须精确匹配，不支持通配符、路径前缀或“同类动作”泛化。
- 默认策略：R0/R1 可按策略自动处理；R2 精确指纹 24 小时；R3 永不记住。
- 任何授权都可在控制台权限页撤销；到期后必须重新确认。
- 审批记录只证明人作过决定，不自动证明动作已执行或业务已验收。

## 实施分工

| 工作包 | 负责内容 | 依赖 |
| --- | --- | --- |
| Agent A：核心数据与 API | Workspace、Task.workspace_id、历史回填、ApprovalGrant、Executor/Expert/Supervisor 模板、PilotSession/PilotRoute | 无 |
| Agent B：插件协议与懒加载 | manifest `workbench` 扩展、声明式页面 schema、插件页面 API、插件启用范围、能力加载器、启动期零可选模块加载验证 | 无 |
| Agent C：Workbench 模式壳 | 拆分单体 `app.js`，实现模式路由、共享状态、全局切换、工坊和控制台导航；复用现有页面模块 | A、B 接口稳定 |
| Agent D：领航交互与编排 | 输入拆分、追问卡、任务卡、路由改派、并发队列、内联审批、监督建议和专家调用展示 | A、C 契约稳定 |
| Agent E：验收与安全 | 迁移测试、插件沙箱协议、权限绕过测试、并发与恢复测试、桌面端到端测试、100% 增量覆盖率门禁 | 持续参与 |

协作顺序：

1. 先更新本计划涉及的领域词汇、ADR 和 UI 契约，再开始实现。
2. A 与 B 可以并行；C 在 A/B 接口稳定后接入。
3. D 在 A/C 的任务与模式契约稳定后接入。
4. 每个工作包完成后先跑定向测试，再根据真实接口差异小步回改文档和契约。
5. 旧完整工作台只保留开发开关兜底，功能对齐后删除；不长期维护双界面。

## 测试与验收

| 范围 | 验收场景 |
| --- | --- |
| Workspace | 路径规范化、Windows 大小写、重复目录、历史任务回填、未绑定目录、按工作区分组 |
| 模式 UI | 三种导航可见性、模式记忆、共享任务状态、切换模式不中断任务、控制台新建后留在控制台 |
| 插件协议 | manifest 校验、启用/停用、页面懒加载、声明式组件白名单、非法 action 拒绝 |
| 插件安全 | 沙箱 origin、消息白名单、插件无法读取 Token、无法访问主页面 DOM |
| 领航 | 多任务拆分、阻塞追问、路由理由、用户改派、并发 3/上限 8、排队、单任务单执行 Agent |
| 专家与监督 | 专家只读、预算扣除、监督硬门、监督建议不拥有执行权、最终验收分离 |
| 审批 | 指纹精确匹配、跨工作区拒绝、TTL 过期、撤销、R2/R3 限制、重复提交幂等 |
| 懒加载 | 默认启动不加载可选能力；页面未打开不请求资源；加载失败不影响内核启动 |
| 回归与安全 | 原生会话、Craft 会话、审批、队列恢复、模型配置、桌面桥接、路径穿越、伪造插件 ID、跨工作区越权 |

覆盖率要求：新增和修改的生产代码达到行、函数、分支 100%；优先运行直接相关测试，公共基础能力或影响范围无法可靠判断时扩大回归范围。保留现有未提交改动，不清理无关文件。

## 假设与非目标

- 首版不允许并行写入多个工作树；并行只用于只读研究和不同任务之间。
- 首版插件页面先交付声明式协议，沙箱 iframe 作为第二里程碑；首版不允许插件注入普通 HTML/JS。
- 插件全局安装、按工作区启用；插件元数据常驻，运行时和页面按需加载。
- “其他”导航删除；高级诊断、评测和剩余配置放入设置或对应插件页。
- 领航默认并发 3、上限 8；并发设置是全局设置，首版不做工作区级覆盖。
- 首次进入领航，之后恢复上次模式；旧完整工作台只保留开发开关兜底，功能对齐后删除。
- 不新增第二套 Runtime、第二套 Approval 或第二套 Task Store；所有模式继续使用现有 Craft 事实链。
- 不自动发布执行模板、专家模板或插件页面；候选必须经过现有评测与 Signoff 流程。
- 不承诺首版支持跨设备同步、插件市场分发、任意第三方 Agent 远程执行或并行写入自动合并。
